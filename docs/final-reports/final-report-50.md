### 3. Existing appointment conflict behavior
Конфликт автомобиля:
- проверяется запросом `findConflict`: тот же автомобиль, активные статусы, полуоткрытое пересечение, исключение самой записи;
- при конфликте — `409 APPOINTMENT_CONFLICT` с `conflictingAppointmentId`.

До Prompt 50 проверка и вставка шли без транзакции и блокировки. Теоретически это допускало гонку и для автомобиля. Теперь проверка автомобиля выполняется под той же блокировкой, что и проверка мощности (§16).

### 4. Capacity model decision
- **`Business.serviceBayCapacity Int @default(1)`** — одно число на бизнес. Название — из промпта; оно согласуется с английскими именами полей в схеме.
- **Значение по умолчанию — 1.** Аудит данных (§8) не нашёл ни одного пересечения, так что 1 безопасно для всех.
- Не вводились: отдельные посты и подъёмники, мастера, мощность по услугам, привязка записи к конкретному посту.
- Термин в интерфейсе — «Количество постов»; в продукте слово «пост» ранее не использовалось в другом значении.

### 5. Statuses consuming capacity
| Статус | Занимает пост |
|---|---|
| `SCHEDULED`, `CONFIRMED`, `IN_PROGRESS` | **да** |
| `COMPLETED`, `CANCELLED`, `NO_SHOW` | нет |

- Это ровно тот же набор, что блокирует автомобиль. Одно определение «активной записи»: `CAPACITY_CONSUMING_STATUSES` в `domain/capacity.ts`, а `CONFLICT_BLOCKING_STATUSES` теперь строится из него; совпадение закреплено тестом.
- Жизненный цикл не возвращает терминальную запись в активный статус. Поэтому смена статуса сама по себе никогда не начинает занимать пост.

### 6. Interval/overlap semantics
- Везде полуоткрытый интервал `[startAt, endAt)`: конфликт автомобиля, мощность, доступность.
- 10:00–11:00 и 11:00–12:00 не пересекаются; 10:59–12:00 пересекается (оба случая закреплены тестами).
- **Загрузка = пиковая одновременность, а не число пересекающихся записей.** Считается алгоритмом sweep-line внутри интервала. Именно так определено в §1 («не больше N в любой момент»).
  - Пример: при 2 постах записи 10:00–10:30 и 10:30–11:00 никогда не идут одновременно. Поэтому 10:00–11:00 ещё помещается; простой подсчёт пересечений ошибочно отказал бы.
  - Условие приёма: `peak(существующие) + 1 ≤ serviceBayCapacity`.

### 11. Availability API
`GET /api/appointments/availability` — новый маршрут, только чтение, для любой авторизованной роли.

- **Параметры запроса:** `serviceId`, `startAt` (ISO 8601 со смещением); необязательные — `endAt` (по умолчанию `startAt` + длительность услуги), `vehicleId`, `excludeAppointmentId`.
- **Сервер определяет сам** по сессии: бизнес, часовой пояс, часы и мощность.
- **Ответ:**
  ```json
  { "availability": { "startAt", "endAt", "timezone", "available",
    "reasons": [{ "code": "OUTSIDE_WORKING_HOURS|VEHICLE_CONFLICT|CAPACITY_EXCEEDED", "message": "…" }],
    "capacity": { "capacity", "occupied", "remaining", "available" } } }
  ```
- **Не раскрывается:** id и содержимое чужих записей.
- **Ошибки:** невалидный запрос → 400; чужие или неизвестные `serviceId` / `vehicleId` → 404; другой метод → 405.

### 12. Create validation
Порядок в `createAppointment`:
1. владение и активность клиента / автомобиля / услуги;
2. длительность;
3. рабочие часы;
4. **в одной транзакции:** блокировка бизнеса → повторное чтение мощности из заблокированной строки → конфликт автомобиля → мощность → вставка.

- Нет свободного поста → **`409 CAPACITY_EXCEEDED`**, «На выбранное время нет свободных постов.».
- В ответе нет `details`: какие записи занимают посты, клиенту знать не нужно.
- Код ошибки следует принятому соглашению (409 + конкретный код, как у `APPOINTMENT_CONFLICT`).
- Все экраны создания и изменения записей уже показывают `error.message` сервера. Поэтому текст виден без изменений интерфейса: «Записи», перенос из карточки записи, создание записи из заявки.

### 13. Update/reschedule validation
| PATCH | Блокировка | Мощность |
|---|---|---|
| только статус / заметки | нет | нет — в том числе в старом «переполненном» слоте |
| смена автомобиля / клиента / услуги без смены времени | да (проверка автомобиля) | нет: интервал тот же, лишний пост не занимается |
| перенос / новый `endAt` (новая длительность) при активном итоговом статусе | да | **да**, сама запись исключена из подсчёта |
| перенос с одновременной отменой | да | нет: запись освобождает пост, а не занимает его |

Итоговый статус определяется как `input.status ?? existing.status`. Терминальные записи переносить нельзя, как и раньше.

### 14. Vehicle-conflict coexistence
Два отдельных правила, оба обязательны. При мощности 3 и свободных постах тот же автомобиль на пересекающееся время по-прежнему получает `409 APPOINTMENT_CONFLICT` (а не отказ по мощности); это закреплено тестом. Если нарушены оба правила, первым отвечает конфликт автомобиля как более конкретный.

### 15. Business-hours coexistence
- Рабочие часы проверяются до транзакции, тем же `assertWithinWorkingHours`; второй реализации нет.
- Свободные посты не отменяют часы работы. Тесты с мощностью 5: до открытия, после закрытия и в выходной — 400.
- Запись, заканчивающаяся ровно в момент закрытия, допустима, и мощность действует и здесь.

### 16. Concurrency strategy
Используется `businessRepository.lockForScheduling`:

```sql
SELECT "serviceBayCapacity" FROM "businesses" WHERE "id" = $1 AND "tenantId" = $2 FOR NO KEY UPDATE
```

- **Где:** внутри `runInTransaction` (Prompt 48.1), той же схемой, что в Prompt 48.1 / 49. Порядок: блокировка → повторное чтение → подсчёт → запись → commit. Любая ошибка откатывает всю транзакцию.
- **Почему `FOR NO KEY UPDATE`, а не `FOR UPDATE`.** Блокировка сериализует бронирования и правки профиля только **этого** бизнеса. Она не мешает вставкам, которые лишь ссылаются на бизнес (клиенты, сообщения и т. д.): они берут `FOR KEY SHARE`, а тот с `FOR NO KEY UPDATE` не конфликтует. Остальные бизнесы не затрагиваются, база целиком не блокируется.
- **Мощность читается из заблокированной строки**, а не из контекста запроса. Если администратор только что снизил мощность, действует новое значение (закреплено тестом).
- Под той же блокировкой теперь проверяется и конфликт автомобиля. Это закрывает прежнюю теоретическую гонку «двойной записи одного автомобиля».

### 18. Tenant isolation
- **Блокировка:** `WHERE id AND tenantId`. Для чужого бизнеса ничего не блокируется и возвращается `null` (тест проверяет SQL и параметры).
- **Запрос загрузки:** `tenantId + businessId`, активные статусы, ограниченное окно (тест проверяет точный `where`). Записи другого тенанта и другого бизнеса не учитываются (тест).
- **Изменение мощности:** только для бизнеса из сессии, `updateMany … WHERE id AND tenantId`. Чужой id → 0 строк (тест). Manager изменить мощность не может (403).
- **Доступность:** считается только по своему бизнесу. Чужие `serviceId` / `vehicleId` → 404. Узнать число записей другого тенанта нельзя.
- **Supabase:** тенант `check3` поменял мощность → изменилась только его запись, у `check4` осталось 1; значение `check3` восстановлено. `check3` с услугой `check4` → 404.

### 19. Timezone validation
Сравнение идёт по мгновениям UTC, а часы и дни — в `Business.timezone`. Часовой пояс браузера не используется. Новых библиотек нет.

- **Europe/Moscow:** дневной интервал; граница закрытия (17:00–18:00 допустимо, 17:30–18:30 — нет).
- **Asia/Kamchatka (UTC+12):** запись в понедельник 09:00 хранится как **воскресенье** 21:00Z. Она учитывается для локального понедельника: пересекающаяся запись получает отказ, генератор слотов не предлагает 09:00.
- **America/New_York (DST, EDT):** 09:00 по местному времени = 13:00Z. Запрос на 09:00Z (05:00 по местному) — `OUTSIDE_WORKING_HOURS`, при этом пост свободен.

### 20. Performance/query/index assessment
- **Проверка мощности — один запрос:**
  ```
  tenantId, businessId, status IN (…),
  startAt < end AND startAt > start − 24 h AND endAt > start
  ```
  Нижняя граница по `startAt` корректна: длительность записи ≤ 24 ч — это инвариант `assertDuration` и Zod. Благодаря ей запрос использует **существующий** индекс `(tenantId, businessId, startAt)` как ограниченный диапазон, а не сканирует всю историю.
- **Генератор слотов:** один такой запрос на день плюс вычисление в памяти. Раньше не было ничего, стало O(1) запросов. Прежний `findConflict` на слот (только при заданном `vehicleId`) не менялся.
- **Новый индекс не нужен.** Запрос покрывается существующим индексом, спекулятивных индексов нет.
