## Final Report — Prompt 56: Booking Confirmation Flow

Заявка (CustomerRequest) → реальные свободные слоты → оператор выбирает слот →
явное «Подтвердить запись» → запись (Appointment) создаётся каноническим
сервисом записей → заявка связывается с записью и (по правилам жизненного
цикла) преобразуется — атомарно, в одной транзакции под блокировкой Prompt 50.
Тот же блок «Запись» встроен в карточку заявки и в карточку диалога. AI в
бронировании не участвует, клиенту ничего не отправляется. Без изменений схемы.

Реализация шла в двух сессиях: первая упёрлась в лимит сессии после написания
кода и тестов (тесты ещё не запускались); вторая продолжила с рабочего дерева,
ничего не откатывая (см. продолжение в `docs/prompts/prompt-56.md`).

---

### 1. Audit findings

- **CustomerRequest**: `customerId` (обязателен), `vehicleId?`, `serviceId?`,
  `appointmentId?` (FK на Appointment, Restrict), `requestedDate` (UTC-полночь
  локальной даты бизнеса), `requestedTimeFrom/To` («HH:mm», бизнес-время).
- **Appointment**: `customerId`, `vehicleId`, `serviceId` обязательны, `startAt/endAt` UTC.
- **Связь**: заявка → запись через `CustomerRequest.appointmentId` (одна запись на заявку).
- **Статусы заявки** (`customerRequestService.ALLOWED_TRANSITIONS`):
  NEW → IN_PROGRESS → (WAITING_CUSTOMER ↔ IN_PROGRESS) → QUALIFIED → CONVERTED;
  CONVERTED/CLOSED/CANCELLED терминальные. **CONVERTED достижим только из
  QUALIFIED** и только при связанной записи; связь и смена статуса — два
  отдельных действия (Prompt 27/31).
- **Существующий quick-create (Prompt 31) в Request Detail**: `POST
  /api/appointments`, затем отдельный `PATCH` заявки с `appointmentId` — **два
  неатомарных вызова** (возможна «сиротская» запись при сбое второго шага),
  оператор мог выбрать другой автомобиль/услугу, статус не менялся.
- **Prompt 50**: `createAppointment` → `withSchedulingLock` (SELECT … FOR NO KEY
  UPDATE строки бизнеса, повторная проверка конфликта автомобиля и ёмкости под
  блокировкой). Рабочие часы/длительность/активность — до транзакции.
- **Prompt 51**: `checkAvailability` (сетка 30 мин, часы, длительность услуги,
  ёмкость, конфликты автомобиля, прошедшие слоты отсекаются) + `GET
  /api/appointments/availability?date=`; клиентский `AppointmentTimeField`.
- **Prompt 48**: при CONVERTED связанный follow-up переводится в BOOKED в той же транзакции.
- **Отмена записи** (CANCELLED/NO_SHOW) никак не трогает заявку — так и оставлено.
- Блокировки строки заявки не было; паттерн `findByIdForUpdate` есть у
  conversation и service follow-up.
- Изменение схемы **не требуется**.

### 2. Existing booking architecture reused

- **Создание записи** — только канонический `createAppointment` (Prompt 50):
  проверки владения/активности клиента, автомобиля, услуги; длительность;
  рабочие часы; конфликт автомобиля и ёмкость — под блокировкой бизнеса.
  Добавлены лишь необязательные **транзакционные хуки** `afterLock` /
  `afterCreate`. Без хуков поведение идентично, все тесты Prompt 50 зелёные.
- **Слоты** — `GET /api/appointments/availability` (day mode) и компонент
  `AppointmentTimeField` из Prompt 51. Расширен необязательными пропсами:
  `allowManual`, `isPreferred`, `preferenceHint`, `narrow`; по умолчанию
  поведение `/appointments` прежнее.
- **Переходы статусов** — та же таблица `ALLOWED_TRANSITIONS` (экспортирован
  предикат `canTransitionRequest`).
- **Follow-up hook** Prompt 48 (`markBookedByCustomerRequest`) — в той же транзакции.
- Никаких расчётов доступности в компонентах, AI-слое или новом сервисе нет.

### 3. Booking readiness rules

Готовность = то, что реально требует `createAppointment`:
- **активный клиент**;
- **активный автомобиль** этого клиента;
- **активная услуга**.

Названия недостающего (`bookingMissing`):
- «клиент» / «активный клиент»;
- «автомобиль» / «активный автомобиль»;
- «услуга» / «активная услуга».

Чего не требуется:
- VIN, госномер, email — не требуются;
- **желаемая дата не требуется**: запись бронирует интервал, который оператор
  выбирает в сетке; дата заявки — лишь пожелание.

Состояния (`state`):
- `booked`;
- `ready`;
- `not_ready`;
- `closed` — CLOSED/CANCELLED без записи;
- `inconsistent` — CONVERTED без записи или ссылка на отсутствующую запись.

### 4. Request source-of-truth behavior

- Клиент, автомобиль и услуга берутся **только из сохранённой заявки** на
  сервере. AI-предложение Prompt 55 не используется.
- Браузер присылает лишь `{ startAt, expectedRequestUpdatedAt }`. Схема
  `.strict()`, поэтому любые `customerId` / `vehicleId` / `serviceId` /
  `appointmentId` / `tenantId` / `endAt` дают 400.
- `endAt = startAt + Service.durationMinutes`, так же как в генераторе слотов.
- **Версия заявки**:
  - `expectedRequestUpdatedAt` сверяется до транзакции, затем повторно под
    блокировкой строки заявки вместе со статусом, клиентом, автомобилем и
    услугой;
  - любое расхождение даёт 409 `BOOKING_STALE` «Данные заявки изменились.
    Обновите страницу и попробуйте ещё раз.»

### 5. Preferred-time semantics

- `requestedDate` выбирает начальную дату сетки, если она не в прошлом.
- `requestedTimeFrom/To` — **окно пожелания**. Модель хранит именно диапазон
  (from/to), поэтому интерпретация такая:
  - «после 15:00» → слот начинается не раньше 15:00;
  - «до 18:00» → слот заканчивается не позже 18:00.
- Подходящие слоты **подсвечиваются** (`data-preferred`) с поясняющей строкой.
  **Остальные свободные слоты остаются доступны**: это не жёсткое ограничение.
- Пожелание ничего не резервирует. Текст: «Пожелание клиента: 2 октября, после
  15:00 — это не бронь, время выбирается ниже.» Слоты всегда запрашиваются
  заново; подтверждённое время показывается только при существующей записи.

### 6. Availability UX

- «Подобрать время» открывает поле даты, предзаполненное пожеланием.
- Дальше — сетка реальных свободных слотов из того же endpoint и того же
  компонента, что и в `/appointments`, в бизнес-часовом поясе.
- В потоке бронирования **только слоты**: «Указать время вручную» скрыт,
  потому что сервер принимает лишь начало и длительность услуги. Запись
  нестандартной длительности по-прежнему создаётся в `/appointments`.
- В узкой колонке карточки диалога сетка строится по ширине слота
  (`auto-fill, minmax(4rem,1fr)`), а не по ширине экрана.

### 7. Explicit confirmation UX

- **Выбор слота ничего не пишет** (проверено: ни записи, ни изменений заявки).
- После выбора показывается блок «Проверьте запись»:
  - клиент, автомобиль, услуга;
  - дата («5 октября»), время («15:30–16:30»), длительность («60 минут»);
  - что будет со статусом: «Заявка будет отмечена как «Преобразована»» или
    «Статус заявки («Новая») не изменится — запись будет связана с заявкой»;
  - «Клиенту ничего не отправляется.»
- Мутация происходит только по кнопке «Подтвердить запись». Во время запроса
  кнопка показывает «Создание записи…» и заблокирована (state + ref).
- **Ошибки**:
  - «время ушло» (`CAPACITY_EXCEEDED`, `APPOINTMENT_CONFLICT`,
    `OUTSIDE_WORKING_HOURS`, `BOOKING_TIME_PASSED`): выбор сбрасывается, слоты
    перезапрашиваются, другое время автоматически не выбирается;
  - «заявка изменилась» (`BOOKING_STALE`, `SERVICE_INACTIVE`,
    `BOOKING_NOT_READY` и др.): состояние заявки перечитывается.

### 8. Appointment creation path

`POST /api/customer-requests/:id/booking` → `confirmRequestBooking`:

1. Роль: owner, admin или manager.
2. Заявка своего тенанта и бизнеса; иначе 404.
3. Уже связана → вернуть существующую запись (`created:false`).
4. Терминальный статус → 409 `REQUEST_FINISHED`; CONVERTED без записи → 409
   `REQUEST_INCONSISTENT`.
5. Проверка версии.
6. Готовность:
   - нет автомобиля или услуги → 400 `BOOKING_NOT_READY`
     («Для записи не хватает: …»);
   - неактивная услуга, автомобиль или клиент → 400 `SERVICE_INACTIVE`,
     `VEHICLE_INACTIVE` или `CUSTOMER_INACTIVE`.
7. `startAt` в прошлом → 409 `BOOKING_TIME_PASSED`.
8. `createAppointment(...)` с хуками; всё остальное перепроверяет канонический
   путь.

Ошибки канонического пути переводятся в русские сообщения, коды сохраняются:
- `CAPACITY_EXCEEDED` → «Это время уже занято. Выберите другое свободное время.»;
- `APPOINTMENT_CONFLICT` → «Автомобиль уже записан на это время. Выберите
  другое свободное время.» (без `conflictingAppointmentId`);
- 400 по рабочим часам → 409 `OUTSIDE_WORKING_HOURS`.

SQL, Prisma и стек наружу не уходят.

### 9. Atomic conversion behavior

Одна транзакция `withSchedulingLock`:

1. Блокировка строки бизнеса (Prompt 50).
2. `afterLock`: `customerRequestRepository.findByIdForUpdate`
   (SELECT … FOR UPDATE по id, tenantId и businessId) и повторная проверка:
   - уже есть `appointmentId` → «уже записано»;
   - изменились статус, `updatedAt`, клиент, автомобиль или услуга → 409.
3. Проверка конфликта автомобиля и ёмкости под блокировкой (Prompt 50).
4. INSERT записи.
5. `afterCreate`: `linkBookedAppointment` — compare-and-set
   `WHERE appointmentId IS NULL AND status = <проверенный>`, плюс строка
   истории при смене статуса, плюс follow-up → BOOKED при CONVERTED.
   0 строк → 409 `BOOKING_STALE`.
6. Любой throw откатывает всё. Состояния «запись есть, заявка не связана» и
   «CONVERTED без записи» невозможны (покрыто тестами со сбоем вставки и
   сбоем связывания).

Порядок блокировок везде одинаковый — бизнес, затем заявка. Других путей,
которые блокируют заявку раньше бизнеса, нет.

### 10. Request status transition

- **QUALIFIED → CONVERTED**: единственный легальный путь в CONVERTED.
  Выполняется в той же транзакции со строкой истории (автор — оператор).
- **NEW / IN_PROGRESS / WAITING_CUSTOMER**: запись создаётся и связывается,
  **статус не меняется**, без фиктивных переходов и без обхода валидации.
  Оператор может позже провести заявку через QUALIFIED → CONVERTED
  существующим селектором статуса (связь уже есть).
- Нового статуса BOOKED нет. Значение CONVERTED прежнее: «есть связанная запись».

### 11. Existing-Appointment behavior

- **Заявка со связанной записью**: показывается только запись — дата · время,
  автомобиль, услуга, статус записи, «Открыть запись →»
  (`/appointments?open=`). Кнопки создания нет. Повторный POST возвращает 200
  `created:false` с той же записью.
- **Связанная запись позже CANCELLED / NO_SHOW**: связь и статус заявки
  сохраняются, замена не создаётся, статус не откатывается (поведение до
  Prompt 56 сохранено, тест есть).
- **CONVERTED без записи** (несогласованные legacy/тестовые данные):
  предупреждение «Заявка отмечена как преобразованная, но связанная запись не
  найдена. Новая запись не создаётся — проверьте заявку.» и 409
  `REQUEST_INCONSISTENT`; ничего не создаётся.

### 12. Idempotency / double-submit protection

- **Сервер**: блокировка строки заявки под блокировкой бизнеса. Вторая
  конкурирующая попытка видит связь первой и получает 200 `created:false`
  (не 409 из-за конфликта автомобиля).
- **Страховка на уровне БД**: compare-and-set по `appointmentId IS NULL`.
- **UI**: кнопка блокируется на время запроса (state + синхронный ref);
  это дополнение, а не защита.
- **Результат**: не более одной записи на заявку при двойном клике, повторе
  браузера, двух вкладках и двух операторах.

### 13. Capacity race behavior

Слот был свободен, а последний пост занят раньше подтверждения:
- блокировка Prompt 50 даёт 409 `CAPACITY_EXCEEDED`;
- транзакция откатывается: записи нет, заявка не изменена (`updatedAt` тот же),
  статус прежний;
- UI показывает «Это время уже занято. Выберите другое свободное время.»,
  сбрасывает выбор и перезапрашивает слоты (занятый слот исчезает);
- другое время автоматически не выбирается.

### 14. Vehicle-conflict behavior

- Пересекающаяся запись того же автомобиля (например, из другой заявки) даёт
  409 `APPOINTMENT_CONFLICT` «Автомобиль уже записан на это время…».
- Заявка не изменена, слоты перезапрашиваются; генератор слотов скрывает
  интервалы занятого автомобиля.

### 15. Service/hours/capacity stale-state behavior

- **Услуга деактивирована**: GET переводит заявку в `not_ready` («активная
  услуга»); POST даёт 400 `SERVICE_INACTIVE` «Услуга больше недоступна для
  записи. Выберите другую услугу.» Подмены нет.
- **Рабочие часы изменились**: проверка канонического пути даёт 409
  `OUTSIDE_WORKING_HOURS` и перезапрос слотов.
- **Ёмкость уменьшена**: используется ёмкость, прочитанная под блокировкой,
  а не значение из сессии или клиента (тест «capacity lowered»).
- **Время прошло** (страница была открыта долго): 409 `BOOKING_TIME_PASSED`.

### 19. Security / tenant isolation

- Без сессии → 401 (GET и POST).
- Чужая или неизвестная заявка → 404 (GET и POST, через сервис и через HTTP).
- Подмена id в теле (customer, vehicle, service, appointment, tenant, endAt) →
  400, `.strict()`; канонические id заявки переопределить нельзя.
- Чужой клиент, автомобиль или услуга недостижимы: id берутся из заявки,
  которая сама проходит проверку тенанта, а `createAppointment` повторно
  проверяет их через `tenantId` и `businessId`.
- Чужую запись привязать нельзя: связывается только что созданная.
- `tenantId` клиента никогда не используется — только `AuthContext`.
- SQL блокировки заявки и compare-and-set привязки закреплены в
  `tenantIsolation.test.ts`: `"id" = $1 AND "tenantId" = $2 AND "businessId" = $3`
  и `WHERE … tenantId, businessId, appointmentId: null, status`.
