# Final Report — Prompt 27: Service Workflow & Request Lifecycle Audit v1

## 1. Audit Summary

Audited every model that could plausibly participate in a CustomerRequest
lifecycle: `CustomerRequest`, `Conversation`, `Message`, `Customer`,
`Vehicle`, `ServiceRecord`, `AiEscalation`, `AiLog`, and `Appointment`
(`prisma/schema.prisma`, cross-checked against `customerRequestService.ts`,
`appointmentService.ts`, and every relevant API route). No WorkOrder, Job,
ServiceOrder, Invoice, Payment, Technician, or Schedule model exists
anywhere in the codebase.

## 2. CustomerRequest Lifecycle

Real `CustomerRequestStatus` enum (unchanged since Prompt 07):
`NEW, IN_PROGRESS, WAITING_CUSTOMER, QUALIFIED, CONVERTED, CLOSED, CANCELLED`.

Real, enforced transition table — audited directly from
`customerRequestService.ts`'s own `ALLOWED_TRANSITIONS` constant and its
`assertValidTransition()` guard (called on every `PATCH`):

| Current | Available next statuses |
|---|---|
| NEW | IN_PROGRESS, CLOSED, CANCELLED |
| IN_PROGRESS | WAITING_CUSTOMER, QUALIFIED, CLOSED, CANCELLED |
| WAITING_CUSTOMER | IN_PROGRESS, CLOSED, CANCELLED |
| QUALIFIED | CONVERTED, CLOSED, CANCELLED |
| CONVERTED | *(none — terminal)* |
| CLOSED | *(none — terminal)* |
| CANCELLED | *(none — terminal)* |

This is the backend's real, already-enforced rule set — nothing here was
invented; it was previously just not reflected in the frontend's status
controls (which offered all 7 values regardless of the current status).

## 4. `CONVERTED` Meaning

Confirmed directly in `customerRequestService.ts::updateCustomerRequest`:
a request may only be transitioned to `CONVERTED` if it already carries a
non-null `appointmentId` — the backend throws
`"Cannot mark a customer request as CONVERTED without a linked
appointment"` otherwise. A `CONVERTED` request additionally can never
have its `appointmentId` cleared again (a second, explicit guard). So
`CONVERTED` concretely means: *this inquiry became a real, scheduled
Appointment* — not just a status label with no further meaning.

## 5. Service History

Unchanged from the Prompt 26 audit: `ServiceRecord` is a real, direct
child of `Vehicle` (required `vehicleId` FK) and also links `Customer`,
`Service`, and optionally `Appointment`. It has no direct relation to
`CustomerRequest` at all — the two are siblings under `Vehicle`, not
parent/child. It is a historical log of completed work
(`performedAt`, `workDescription`, `totalPrice`, etc.), created manually
via its own existing form, not auto-generated by any request/appointment
transition.

## 6. Product Decision

**A. Existing downstream workflow implemented.** `CustomerRequest.CONVERTED`
→ `Appointment` is a real, already-existing relation and entity — this
prompt connected the two more visibly in Request Detail and made every
existing status control respect the backend's real transition rules,
without creating any new business entity.

## 7. Implementation

- Frontend `NEXT_STATUSES` map added, mirroring the backend's
  `ALLOWED_TRANSITIONS` exactly (§2). Both of Request Detail's status
  controls (header quick-change select, edit-form select) and the
  Operations work queue's quick status-change control now only offer the
  request's real current status + its real allowed next statuses.
  Terminal statuses show a plain badge (header) or a disabled
  single-option control (Operations), never an offer to "transition" out
  of a state that has no valid next state.
- A one-click **"Взять в работу"** button was added for `NEW` requests
  (the literal `NEW → IN_PROGRESS` example from spec STEP 8), calling the
  same existing `PATCH` endpoint the status select already used.
- A new **"Запись"** (Appointment) section was added to Request Detail:
  - If `appointmentId` is set: fetches and shows the real linked
    appointment's date/time/status (`GET /api/appointments/:id`) with a
    link into the existing `/appointments` screen.
  - If status is `QUALIFIED` and no appointment is linked yet: shows
    real, accurate next-step guidance ("link an existing appointment via
    Edit, then transition to CONVERTED") — not a fabricated "create
    appointment" button, since building appointment-creation UI here was
    explicitly out of this prompt's scope.

## 15. Limitations / Product Gaps

- **No downstream-of-CONVERTED workflow beyond the Appointment link
  itself.** Once CONVERTED, the request is genuinely terminal in this
  codebase — there is no WorkOrder/Job to track the actual mechanical
  work, no technician assignment, no parts/labor breakdown tied to the
  request. `ServiceRecord` (service history) exists as a separate,
  manually-created historical log, with no automatic link from either
  the CustomerRequest or the Appointment that preceded it. **If a future
  prompt wants a real "Appointment completed → ServiceRecord created"
  workflow, that relation does not exist today and would need a real
  product decision (and possibly a schema change) — not something to
  infer from the current data.**
- **No appointment-creation flow from Request Detail.** An admin who
  wants to move a `QUALIFIED` request toward `CONVERTED` must still
  create the Appointment separately (via `/appointments`) and then link
  it through Request Detail's existing Edit form — there is no
  "Создать запись из этой заявки" shortcut. This was a deliberate scope
  boundary (STOP CONDITION explicitly warns against adding scheduling/
  appointment functionality "заодно"), not an oversight.
- **Conversation Detail has no "back to the request" link.** Out of
  scope for this prompt (would require touching Conversation Detail
  itself, not the Request lifecycle).
- **`AppointmentsSettingsPage` (`/appointments`) still has no per-item
  detail/`?open=` mechanism** — the new "Запись" section in Request
  Detail links to the general `/appointments` list, not a specific
  appointment, for the same reason Vehicle Detail's Service History
  section links to a filtered list rather than a nonexistent per-item
  detail page. Building that mechanism was out of this prompt's scope.
