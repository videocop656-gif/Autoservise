## Final Report — Prompt 57: Customer-First / Missed Call Recovery Architecture Audit

Аудит и документация. Production-код, Prisma-схема, миграции, поведение
приложения и стартовый экран **не менялись**. Подробный документ с полными
таблицами: [`docs/audits/missed-call-recovery-architecture-audit.md`](../audits/missed-call-recovery-architecture-audit.md).

### 1. Executive summary

Новое направление: AUTOSERVISE не «ещё одна CRM», а **«не потерять клиента,
до которого мастер не успел взять трубку»**.

**Готово**, и это переиспользуется без изменений — середина и конец пути
клиента:
- диалог;
- приём клиента и автомобиля (P54);
- разбор обращения (P55);
- заявка;
- реальные свободные слоты и ёмкость (P50–51);
- атомарная запись из заявки (P56);
- эскалации и рабочая очередь;
- AI со строгими правилами по ценам и диагнозу.

**Отсутствует целиком** начало пути, а это и есть продукт:
- телефония и событие звонка;
- телефон как первоклассная идентичность;
- реальный WhatsApp (сейчас mock);
- маршрутизация каналов и первое сообщение восстановления;
- автоматический ответ AI;
- хранилище учётных данных по тенантам;
- системный актор;
- фоновое выполнение.

Голосовой AI-ресепшн для MVP не нужен: схема «пропущенный звонок →
мгновенное текстовое сообщение → короткий полезный диалог» ложится на
текущую архитектуру, как только появятся приём события звонка и исходящий
канал.

**Первый промпт реализации — MCR-1 «Phone Identity Foundation».**

### 3. Current architecture strengths

- **Граница `ChannelAdapter`**: нормализованные входящие и исходящие
  сообщения; тенант никогда не берётся из payload.
- **Идемпотентность входящих**: `ChannelMessage` уникален по
  (подключение, externalMessageId).
- **Один диалог на внешний тред**: find-or-create по (подключение,
  externalConversationId), защищённый от гонок.
- **Отслеживание доставки** `ChannelDelivery`: статусы, попытки,
  compare-and-set захват, безопасная таксономия ошибок.
- **Вебхук с маршрутизацией по URL подключения** и проверкой секрета до
  любого чтения из БД.
- **Безопасное разрешение клиента**:
  - сначала идентичность, затем ровно одно активное совпадение по телефону;
  - без автосоздания и без слияния.
- **AI**:
  - правила «не придумывать цену» (диапазон / «от» / «цены нет — так и
    скажи») и «не ставить диагноз»;
  - режимы interactive / draft / qualify;
  - эскалации с не более чем одной активной на диалог (гарантия БД);
  - аудит `AiLog`.
- **Бронирование P50–56**: авторитетная ёмкость, слоты, атомарная
  конвертация заявки.
- **Дисциплина изоляции тенантов**: 136 тестов `tenantIsolation`.

### 4. Critical gaps

1. Телефонии нет: ни модели звонка, ни адаптера, ни вебхука, ни реестра
   номеров бизнеса.
2. WhatsApp только mock. Нет:
   - шаблонов и бизнес-инициированного первого сообщения;
   - окна разговора и согласия (opt-in);
   - статусов DELIVERED/READ.
3. Учётные данные **глобальные** (один Telegram-бот на всё развёртывание).
   Хранилища секретов по тенантам нет; `ChannelConnection.config` по
   контракту несекретный.
4. Телефон — свободный текст:
   - нет канонической формы, индекса и уникальности;
   - сопоставление по последним 10 цифрам регэкспом полным сканированием;
     это верно для +7 (KZ/RU), но не в общем случае.
5. Нет системного актора: контекст вебхука — фиктивный `owner` с
   несуществующим `User.id`.
6. Нет фонового выполнения: всё синхронно в запросе, нет очереди и повторов.
7. AI запускается только кнопками оператора; вебхук → AI отсутствует.
8. Цены «тонкие»: нет примечания к цене, флага «итог после осмотра», типа
   цены и цены по классу авто.
9. Локации нет: только текстовый адрес, без координат, ссылки на карту и
   маршрута.
10. Эскалация не «действенная» с телефона:
    - нет «что AI уже сказал» и типа требуемого действия;
    - приоритет всегда NORMAL;
    - нет уведомлений владельцу.
11. Дашборд меряет старый продукт: нет метрик пропущенных звонков,
    восстановления и задержки.

### 6. WhatsApp-first implications

- WhatsApp ложится на существующую границу адаптеров:
  - ID номера WhatsApp — в `externalAccountId`;
  - номер / WA id клиента — в `externalConversationId` / `externalCustomerId`.
- **Принципиально новое**: первое сообщение инициирует бизнес, адресуя его
  по телефону, а не отвечает в существующий тред. Потребуются:
  - шаблоны (идентификатор, язык, параметры) и состояние окна разговора;
  - статусы доставки через вебхук;
  - отписка / «не писать».
- Нужен маршрутизатор с запасным путём: SMS, другой канал или задача
  «перезвонить». Восстановление никогда не теряется молча.
- Telegram — вторичный необязательный адаптер и не определяет модель
  идентичности.

### 7. Telephony requirements

- **Событие на звонок**:
  - стабильный id;
  - номер звонящего, если не скрыт;
  - вызываемый номер бизнеса;
  - время;
  - итог: ANSWERED / NO_ANSWER / BUSY / FAILED.
- **Подпись / секрет проверяются до чтения БД.**
- **Устойчивость** к повторам, дублям и событиям не по порядку; итог
  определяет машина состояний, а не порядок прихода.
- **Маршрутизация** по URL подключения (предпочтительно). При маршрутизации
  по вызываемому номеру нужна глобально уникальная регистрация номера.
- **Скрытый номер**: восстановление невозможно, факт фиксируется.
- **Без голосового AI**, STT/TTS и логики маршрутизации звонков.

### 8. Identity architecture

```
Phone (канонический E.164, в рамках бизнеса)
  ├─ Customer (0..1 активное совпадение; неоднозначность ⇒ не привязывать, не сливать)
  ├─ звонки этого номера в этот бизнес
  ├─ канальные идентичности (WhatsApp, Telegram…) через CustomerChannelIdentity
  └─ Conversation(s) → CustomerRequest → Appointment
```

- **Каноническое поле.** Канонический E.164 рядом со свободным
  `Customer.phone`, с индексом и бэкфиллом. Страна по умолчанию — от бизнеса.
- **Уникальность.** Без уникальности в БД: дубли legacy и общие семейные
  номера допустимы. Работает правило «ровно одно активное совпадение».
- **Общий `ContactPoint`** для первого среза **не нужен**.
- **Неизвестный звонящий** — диалог с `customerId = null`. Привязку делает
  оператор (P54).
- **Конфиденциальность.** Маскирование номеров в логах и AiLog; номер
  в разных бизнесах — разные контексты.

### 9. Services/pricing readiness

| Нужно | Сейчас |
|---|---|
| Фиксированная цена | только как `priceFrom == priceTo` (явного признака нет) |
| «От» / начальная цена | есть (`priceFrom`) |
| Диапазон | есть (`priceFrom` + `priceTo`) |
| Длительность | есть |
| Активность | есть |
| Валюта | есть (у услуги и у бизнеса) |
| Примечание / условия цены | **нет** |
| Флаг «итог после осмотра» | **нет** |
| Цена по классу авто | **нет** (P2: объяснить и передать человеку) |

Разделение ответственности: **`Service` — единственный источник**
предлагаемых услуг, цен, длительности и признака осмотра. **Knowledge** —
свободные пояснения (что входит, подготовка, гарантия, оплата). Цены в
Knowledge не дублировать.

### 10. Knowledge readiness

- **Есть**:
  - услуги, часы работы, текущее время для AI;
  - адрес текстом, телефон / email / сайт;
  - FAQ, оплата, гарантия, подготовка — свободным текстом
    (`KnowledgeCategory`, `BusinessRuleCategory`);
  - ограничения по маркам и работам — через правила;
  - свободное время — слоты P51.
- **Нет**:
  - координат, ссылки на карту, описания маршрута, отправки точки на карте;
  - исключений по праздникам в расписании;
  - признака «нужен осмотр» на уровне услуги.

### 11. AI readiness

- **Совпадает с целью**:
  - не придумывает цены, диагноз только как предположение;
  - `needsHuman` → эскалация;
  - не утверждает, что «передал менеджеру»;
  - защита от prompt injection;
  - контекст с реальными услугами, ценами, знаниями, правилами, часами,
    адресом.
- **Не хватает**:
  - **автоматического режима ответа** — отдельного, выключенного по
    умолчанию, только с чтением, с триггерами остановки (цена неизвестна,
    осмотр, диагноз, спор, «дайте человека», низкая уверенность);
  - стиля «коротко, полезное сразу, спрашивать только недостающее»;
  - структурных флагов цены, чтобы не гадать про осмотр;
  - локации.

### 12. Booking reuse

Путь диалога после пропущенного звонка переиспользует цепочку целиком:
- приём клиента и автомобиля (P54);
- разбор → заявка (P55);
- слоты и ёмкость (P50–51);
- атомарная запись (P56);
- эскалации и рабочая очередь;
- follow-up.

Изменений в пути бронирования не требуется. Согласие клиента на время
превращается в подтверждение оператором. Автономная запись AI вне рамок.

### 13. Handoff readiness

`AiEscalation` (одна активная на диалог, reason / summary) и очередь
Operations — основа.

Для карточки «НУЖНО ДЕЙСТВИЕ» не хватает:
- происхождения «пропущенный звонок 14:32»;
- структурированного «что AI уже сообщил» (можно выводить из отправленных
  сообщений);
- типа требуемого действия и обоснованного приоритета;
- **уведомления владельцу** вне веб-приложения.

### 15. Metrics

- **Воронка**:
  - пропущенные (скрытые номера отдельно);
  - попытка → отправлено → доставлено;
  - ответ клиента → активный диалог;
  - передано человеку;
  - запись из пропущенного;
  - визит.
- **Скорость**: медиана и p90 «пропущен → отправлено» и «пропущен → ответ».
- **Главная метрика**: «Сколько клиентов AUTOSERVISE помог не потерять».
- **Источник**: всё выводится из записи о звонке и существующих
  Conversation / Message / Escalation / Request / Appointment.

### 16. Security

- **Вебхуки**: подпись или секрет до чтения БД, URL на подключение, общие
  401/404, защита от повторов через уникальные ключи.
- **Секреты**: зашифрованное хранилище на подключение (сейчас только
  глобальный env).
- **Маршрутизация**: только на стороне сервера.
- **Номера**: пересечения номеров между тенантами безвредны при скоупинге.
- **PII**: маскирование номеров, хранение звонков, отписка.
- **Автоматизация**: явный системный актор вместо фиктивного owner;
  лимиты на звонящего, бизнес и вызовы AI.

### 19. Recommended implementation sequence

Новая нумерация **MCR** (Missed-Call Recovery). Сначала mock-провайдеры:
вертикальный срез доказывается до выбора вендора, затем реальные адаптеры
подключаются за теми же границами.

| Шаг | Что делает | Схема |
|---|---|---|
| **R0** | Внешнее исследование A–D; не код, параллельно | — |
| **MCR-1** | Phone Identity Foundation | да, малая |

### 20. FIRST implementation prompt recommendation

**MCR-1 — Phone Identity Foundation.**

Объём:
- чистая функция `normalizePhone(raw, defaultRegion)` → E.164 или null
  (сначала +7 KZ/RU, без внешней библиотеки без обоснования);
- регион по умолчанию на уровне бизнеса;
- канонический номер у клиента с индексом и идемпотентным бэкфиллом;
- резолвер по каноническому номеру вместо эвристики «последние 10 цифр» с
  той же политикой «ровно одно совпадение»;

точного изменения**.

Тесты:

- бэкфилл;

- изоляция тенантов;
