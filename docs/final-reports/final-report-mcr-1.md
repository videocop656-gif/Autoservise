## Final Report — MCR-1: Phone Identity Foundation

Телефон клиента стал надёжной идентичностью: единый формат E.164 через
`libphonenumber-js`, регион по умолчанию у бизнеса, индексированный поиск в
рамках бизнеса вместо эвристики «последние 10 цифр», явное идемпотентное
заполнение существующих данных, маскирование для логов. Телефонии, WhatsApp,
SMS, CallInteraction и автоответов AI **нет** — это последующие шаги MCR.

### 3. Normalization library/approach

- **Библиотека** `libphonenumber-js` ^1.13.14, импорт `libphonenumber-js/max`:
  - порт метаданных Google libphonenumber с полной проверкой номеров по
    странам;
  - MIT, без зависимостей, свежий релиз (2026-09);
  - используется только на сервере.
- **Проверка до внедрения:** в проекте телефонной библиотеки не было. Пробный
  разбор подтвердил корректность для KZ (мобильные и Алматы), RU и
  международных номеров (DE, US, UZ, GB, UA).
- **`npm audit`:** находок по новой зависимости нет. Существующие 7 находок
  относятся к другим пакетам и были до MCR-1.
- **Эвристика «последние 10 цифр» удалена** из разрешения идентичности
  (`localSubscriberNumber` и `findActiveByLocalPhoneNumber` больше не
  существуют).

### 4. Exact normalization contract

`src/server/lib/phone.ts` — единственная реализация:

```ts
parsePhone(input, defaultRegion?) →
  { status: 'valid', e164: '+77011234567', country: 'KZ' } | { status: 'empty' } | { status: 'invalid' }
normalizePhone(input, defaultRegion?) → string | null   // e164 или null
isSupportedPhoneRegion(code) → boolean                  // ISO-код, известный библиотеке
maskPhone(input, defaultRegion?) → '+7******4567' | '***'
```

Правила:
- **`empty`** — пустая строка, пробелы, `null`, `undefined`.
- **Номер с «+»** читается как написан и **никогда не переинтерпретируется**
  в регион бизнеса.
- **Номер без «+»** читается в регионе по умолчанию. Без поддерживаемого
  региона это `invalid`: номер не предполагается казахстанским.
- **Идентичностью** становится только номер, который библиотека признала
  **валидным**. Цифры не добавляются: `+8 701…` → `invalid`, а не «исправленный» +7.
- **Пример.** Для KZ одинаково дают `+77011234567`:
  - `+7 701 123 45 67`;
  - `87011234567`;
  - `8 (701) 123-45-67`;
  - `7011234567`;
  - `77011234567`.

### 5. Default-region behavior

- **Поле:** `Business.phoneRegion`, ISO 3166-1 alpha-2. Готового поля страны
  нет ни у Business, ни у Tenant; часовой пояс как замена стране **не
  используется**.
- **Значение по умолчанию** — `'KZ'`: явный продуктовый default при создании,
  рынок запуска. Он же у всех 7 существующих бизнесов.
- **KZ и RU делят +7** и 10-значный национальный номер, поэтому для +7-номеров
  результат одинаков при любом из двух регионов. Регион важен только для
  рынков вне +7.
- **Резервное поведение:** если региона нет или он неизвестен, номера без «+»
  невалидны, номера с «+» работают.
- **Изменение** — в «Настройки → Бизнес», поле «Страна телефонных номеров»:
  - варианты: Казахстан, Россия, Узбекистан, Кыргызстан;
  - API принимает любой поддерживаемый библиотекой ISO-код и приводит его к
    верхнему регистру; неизвестный код → 400.

### 6. Customer storage behavior

- `customerService.prepareCustomerCreate` (используется и экраном «Клиенты»,
  и приёмом из диалога P54) пишет `phoneE164 = normalizePhone(phone,
  business.phoneRegion)`.
- `updateCustomer`: при изменении `phone` поле `phoneE164` пересчитывается.
  Невалидный номер → `null`; без изменения телефона поле не трогается.
- **«Удаление телефона»:** в текущем домене `Customer.phone` обязательный (не
  менее 5 символов), удалить его нельзя. Сценарий «невалидный номер →
  `phoneE164 = null`» покрыт тестом.
- **Решение по невалидным новым номерам:** сохраняется действующая философия
  свободного ввода. Номер принимается как введён (UI не меняется), но
  **идентичностью не становится** (`phoneE164 = null`) и не участвует в
  поиске и в проверке дублей.
- **Других путей записи клиента нет:** `seed.ts` клиентов не создаёт;
  канальный конвейер клиентов не создаёт по дизайну.

### 7. Lookup behavior

- `customerRepository.findActiveByPhoneE164(tenantId, businessId, e164)` —
  индексированный запрос Prisma по равенству. Тенант и бизнес всегда в
  условии, только активные клиенты.
- `resolveCustomerForInbound`:
  - сначала существующая канальная идентичность;
  - затем `normalizePhone(customerPhone, business.phoneRegion)` и поиск;
  - **ровно одно** совпадение → привязка;
  - ноль совпадений, несколько или невалидный номер → диалог остаётся без
    клиента.
- Автоматического создания и слияния клиентов нет.

### 8. Duplicate behavior

- Приём клиента из диалога (P54) проверяет дубль по `phoneE164`. Совпадение
  в этом бизнесе → 409 `CUSTOMER_PHONE_EXISTS` со списком существующих
  клиентов; оператор привязывает существующего.
- Разные записи одного номера дают тот же дубль: `9001112233`,
  `8 (900) 111 22 33`, `+79001112233` против сохранённого `8 900 111-22-33`.
- **Исправление прежней ложной тревоги:** валидный немецкий номер с теми же
  10 последними цифрами (`+49 900 1112233`) больше не считается дублём.
- **Не дубли:** неактивный клиент с тем же номером и клиент другого тенанта —
  как и раньше.

### 9. Migration/backfill result

- **Механизм:** SQL-миграция только добавляет структуру. Заполнение — явный
  идемпотентный скрипт `npm run backfill:customer-phones` (с флагом
  `-- --dry-run`):
  - файлы: `prisma/backfill-customer-phones.ts`, чистая часть в
    `src/server/lib/phoneBackfill.ts`;
  - он идёт по бизнесам и пересчитывает номер той же `normalizePhone` в
    регионе бизнеса;
  - пишет только реально изменившиеся строки, каждая запись ограничена
    `tenantId + businessId + id`;
  - `Customer.phone` не трогает;
  - печатает только счётчики.
- **Порядок развёртывания:** `prisma migrate deploy` → `npm run
  backfill:customer-phones`. До запуска скрипта поиск по номеру просто ничего
  не находит; ложных совпадений не бывает.
- **Результат на dev-базе:**

  | Прогон | Бизнесов | Клиентов | Валидных | Невалидных | Пустых | Изменено |
  |---|---|---|---|---|---|---|
  | Пробный | 7 | 12 | 12 | 0 | 0 | 0 (значения совпали с ранним SQL-заполнением) |
  | Настоящий | 7 | 12 | 12 | 0 | 0 | 0, записано 0 — идемпотентен |

- **После живой проверки:** 13 клиентов, у 13 есть `phoneE164`. Повторный
  пробный прогон даёт 0 изменений, то есть приложение пишет ровно то же, что
  скрипт.

### 11. Masking behavior

- `maskPhone`: код страны + `*` + последние 4 цифры:
  - `+77011234567` → `+7******4567`;
  - `+998901234567` → `+998*****4567`.
- Невалидное, короткое или пустое значение → `***`; исходник никогда не
  выводится.
- **Аудит нового кода:** ни один новый путь не пишет номера в логи. Скрипт
  заполнения печатает только счётчики, при ошибке — только сообщение без
  данных. В отчёте и логах проверки номера только маскированные.

### 12. Tenant-isolation verification

- `tenantIsolation.test`: поиск идёт с условием `tenantId + businessId +
  isActive + phoneE164`. Тест заменил прежний тест на raw SQL.
- Приём клиента: клиент другого тенанта с тем же номером никогда не
  возвращается и не раскрывается (тест прежний, по-прежнему зелёный).
- Резолвер ограничен бизнесом из `AuthContext` или вебхука, а не из payload.
- **Проверка на живой базе:**
  - один и тот же номер в двух бизнесах не мешает;
  - записи заполнения ограничены тенантом;
  - снимок реальных тенантов не изменился (меняется только общий отпечаток
    связей тестового тенанта).

### 13. Business-phone readiness for MCR-2

`Business.phone` — свободный текст, nullable, не нормализован и не уникален.
**Для маршрутизации «вызываемый номер → бизнес» его недостаточно.**

MCR-2 понадобится отдельная сущность номера бизнеса или подключения
телефонии:
- канонический E.164, нормализованный этой же `normalizePhone` в регионе
  бизнеса;
- **глобальная** уникальность активного назначения номера;
- явный перенос номера между бизнесами.

Альтернатива — маршрутизация по URL подключения, как у Telegram. Спекулятивных
моделей в MCR-1 не добавлялось.

### 18. Known limitations

- **Смена `phoneRegion`** не пересчитывает уже сохранённые номера
  автоматически; нужно повторно запустить `npm run backfill:customer-phones`.
  Для перехода KZ ↔ RU это ничего не меняет (общий +7).
- **`CustomerChannelIdentity.phone`** по-прежнему хранит номер как пришёл: это
  отображаемое поле, ключом не является.
- **Номер бизнеса** не нормализован (см. §13, MCR-2).
- **Невалидные номера** остаются без идентичности; оператор видит их как есть.
  Предупреждения в UI нет — UI вне рамок MCR-1.
- **Метаданные `libphonenumber`** зашиты в версию пакета. Новые диапазоны
  номеров требуют обновления зависимости.
- **`prisma format --check`** не проходит на уже существующей схеме (§15).
- **Телефония, WhatsApp, SMS, CallInteraction, восстановление и автоответы
  AI не реализованы.**
