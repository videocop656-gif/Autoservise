## Final Report — Prompt 54: Customer & Vehicle Intake from Conversation

**Итог: PASS.** В карточке диалога появился раздел **«Клиент и автомобиль»**. Оператор может:
- найти существующего клиента и связать его с диалогом;
- создать клиента с проверкой дубликата по телефону;
- увидеть сохранённые автомобили клиента и добавить новый.

Всё выполняет оператор. Сервер проверяет тенант, роли, дубликаты, согласованность с обращением и параллельные изменения. AI ничего не создаёт и не связывает, ничего не отправляется.

После привязки черновик AI (Prompt 53) получает проверенного клиента и его автомобили через **тот же** канонический контекст. Схема Prisma не менялась, миграций нет.

### 1. Audit findings
- **`Conversation`:**
  - `customerId` — nullable и меняется через общий PATCH (`conversationService.updateConversation` + `assertRelations`);
  - `customerRequestId` защищён (Prompt 49.1);
  - **`vehicleId` нет.**
  - Найден пробел: общий PATCH позволял `customerId: null` при связанном обращении, и диалог начинал противоречить своему обращению.
- **`Customer`:** `firstName`, `lastName?`, `phone` (обязателен, свободный формат), `email?`, `isActive`. Уникальности телефона нет. Есть правило дубликата **email** среди активных (`assertNoActiveEmailDuplicate`). Создание — **owner / admin** (`requireRole`).
- **`Vehicle`:** принадлежит ровно одному `Customer` (`onDelete: Restrict`); VIN и госномер только приводятся к верхнему регистру схемой. **Правил дубликата нет.** Создание — owner / admin.
- **Нормализация телефона:** единственная в проекте — «последние 10 цифр» (`channelCustomerService.localSubscriberNumber` + `customerRepository.findActiveByLocalPhoneNumber`) во входящем конвейере.
- **Поиск клиентов:** `GET /api/customers?search=` — имя, фамилия, телефон, email, `contains` без учёта регистра, только активные, только свой бизнес.
- **Автомобили клиента:** `GET /api/vehicles?customerId=` — только активные.
- **Карточка диалога:** блоки «Клиент» и «Автомобиль» только для чтения; имя бралось из справочника родителя, ограниченного 100 записями. Автомобиль показывался только из связанного обращения.
- **Контекст AI:** клиент — по `conversation.customerId`; автомобиль — **только** через `customerRequest.vehicleId`.
- **Telegram:** в диалоге хранятся `externalConversationId` (= id чата; в личном чате совпадает с id пользователя) и отображаемое имя (в `CustomerChannelIdentity.displayName`, только при совпадении телефона). Telegram не передаёт телефон, username не хранится.

Новых моделей и связей нет.

- **Клиент не привязан:** «Клиент не определён» + «Найти клиента» и «Создать клиента» (вторая — только owner / admin; менеджер видит пояснение).
- **Клиент привязан:** имя (ссылка на карточку), телефон, email; «Сменить клиента», если смена допустима. Ниже — «Автомобили клиента»:

- **Заголовок карточки** берёт имя клиента из ответа самого диалога, а не из ограниченного справочника.

### 4. Customer search behavior
Используется существующий `GET /api/customers?search=` (имя, телефон, email; только активные и только свой бизнес), без нового поискового механизма. Запрос — от 2 символов, задержка 300 мс, до 8 результатов. Клиента выбирает оператор («Связать»); автоматического сопоставления нет.

Поиск по телефону — подстрока сохранённого текста. Например, поиск по 7 последним цифрам найдёт «+79990001122», а «8 (999) 000» — нет. Нормализованное сравнение применяется при **создании** (§6).

### 5. Customer creation behavior
- **Где:** форма в разделе — «Имя»*, «Фамилия», «Телефон»*, «Email» (поля и проверка — существующей схемы).
- **Права:** только owner / admin.
- **Когда:** только если у диалога ещё нет клиента.
- **Как:** создание и привязка — **одна транзакция**.
- **Чего не делает:** Telegram, обращение и запись не затрагиваются.

### 6. Phone normalization / duplicate behavior
- **Перед созданием** ищутся активные клиенты **этого бизнеса** с тем же номером по существующей нормализации «последние 10 цифр». Поэтому «8 (999) 000-11-22» совпадает с «+79990001122».
- **При совпадении** — 409 `CUSTOMER_PHONE_EXISTS` «Клиент с таким номером уже существует.» и до 5 совпадений (имя, телефон). В интерфейсе у каждого кнопка «Связать существующего клиента».
- **Чужой тенант** никогда не ищется и не раскрывается. Неактивные клиенты дубликатами не считаются. Правило дубликата email действует как прежде.
- **Ограничение (без изменения БД):** уникального индекса по телефону нет и не добавлялся — в данных могут быть старые дубликаты, а телефон хранится в свободном формате. Два оператора, одновременно создающие клиента с одним номером **в разных** диалогах, теоретически могут создать двух; в **одном** диалоге гонку закрывает транзакция (§16).

### 7. Existing-Customer linking
`POST /api/conversations/:id/customer`, тело `{ action: "link", customerId, expectedCustomerId }`.

- **Права:** owner / admin / manager — как остальные действия в диалоге.
- **Проверки:** клиент ищется в рамках тенанта (чужой или неизвестный → 404 «Клиент не найден»); неактивный → 400.
- **Если клиент уже привязан** — успех без изменений.

### 8. Relink/unlink safety
- **Смена клиента** — только явная:
  - в интерфейсе «Сменить клиента» → выбор → подтверждение «Сменить клиента диалога на …? / Да, сменить / Отмена»;
  - на сервере `expectedCustomerId` должен совпадать с текущим клиентом — запись идёт как compare-and-set (`setCustomerIfUnchanged`);
  - устаревшая вкладка или чужое более позднее решение → 409 «Данные изменились. Обновите диалог и попробуйте ещё раз.»
- **Отвязки в интерфейсе нет.** Общий PATCH теперь отказывает в `customerId: null`, если связано обращение (400).
- **Ничего не переносится:** сообщения, обращения, записи и автомобили остаются на месте.

### 9. CustomerRequest consistency
- **С обращением:** клиент диалога = клиент обращения. Смена на другого → 409 `CUSTOMER_REQUEST_CONFLICT` «Нельзя изменить клиента: связанное обращение принадлежит другому клиенту.» В интерфейсе «Сменить клиента» скрыта и показано «Клиент определён связанным обращением — сменить его нельзя.»
- **Повторная привязка того же клиента** разрешена.
- **Несовпадение в старых данных** (клиент диалога ≠ клиент обращения) — предупреждение в разделе, автоисправления нет.
- **Защита Prompt 49.1 цела:** intake не принимает и не меняет `customerRequestId` — поле в теле игнорируется (тест). Все тесты 49 / 49.1 проходят.

### 10. Vehicle workflow
- Список — `GET /api/vehicles?customerId=` (активные, только свой тенант).
- «Добавить автомобиль» (owner / admin): «Марка»*, «Модель»*, «Год», «Госномер», «VIN» → `POST /api/conversations/:id/vehicles`.
- **Владелец берётся из диалога на сервере;** `customerId` из тела игнорируется. Без клиента → 409 «Сначала свяжите диалог с клиентом.»
- Создание — через существующий `createVehicle`. Запись и обращение не создаются.

### 11. Vehicle duplicate behavior
- **Единственное надёжное правило:** у **того же** клиента активный автомобиль с тем же VIN или госномером. Оба уже нормализованы схемой: обрезка пробелов + верхний регистр. Совпадение → 409 `VEHICLE_EXISTS` «У клиента уже есть автомобиль с таким VIN или госномером.» с этим автомобилем.
- **Автомобили других клиентов и тенантов** не просматриваются, не раскрываются и не переносятся — совпадающий VIN у другого клиента создаёт отдельный автомобиль (тест).
- **Новые эвристики не вводились** (пробелы внутри номера, латиница / кириллица).

### 12. Vehicle-context persistence decision
**Вариант A из §13. Схема не менялась.**
- У диалога нет `vehicleId`. Канонический «автомобиль работы» — `CustomerRequest.vehicleId`, он выбирается в форме «Создать обращение» (Prompt 49): после intake там сразу доступны клиент и новый автомобиль, родитель перезагружает справочники.
- Раздел показывает **только сохранённое:** автомобили клиента и пометку «в обращении». Ложного «выбранного автомобиля», который пропал бы после перезагрузки, нет.
- Добавлять `Conversation.vehicleId` не потребовалось.

### 13. AI context integration
- **Клиент:** после привязки контекст Prompt 53 получает его через существующий `buildAiContext` — `conversation.customerId`, поиск в рамках тенанта.
- **`customerVehicles`** — новое: до 10 активных сохранённых автомобилей **этого** клиента (марка, модель, год, госномер; без id, VIN и заметок). Это контекст, а не выбор: `vehicle` по-прежнему только из обращения.
- **Правило промпта 22:** `customer` / `customerVehicles` — проверенные данные; что клиент пишет о себе или автомобиле — непроверенные слова, их нельзя выдавать за данные из базы; при нескольких автомобилях — уточнить.
- **Проверено:**
  - в браузере на «Какие мои данные у вас есть?» черновик ответил «По нашим данным: Проверка P48.1, телефон +79990001122.» — данные из базы, а не из текста;
  - в тестах — контекст запроса содержит клиента и автомобили; `vehicle` = null без обращения; ни Message, ни доставки, ни записи.

### 14. Telegram identity findings
- **Что хранится:** id чата (= идентификатор диалога), отображаемое имя.
- **Чего нет:** телефона (Telegram его не присылает в текстовом сообщении), username.
- **Решения в этом промпте:** id чата **не** используется как удостоверение клиента и не приравнивается к телефону. `CustomerChannelIdentity` при ручной привязке не создаётся и не изменяется — диалог, привязанный к чату, и так несёт клиента для всех будущих сообщений этого чата. Полей Telegram в `Customer` не добавлено.

### 16. Transaction/concurrency behavior
- **Создание + привязка** — одна транзакция. Привязка — compare-and-set (`customerId = null`). Если другой оператор успел раньше, транзакция откатывается вместе с новым клиентом (тест: две вкладки одновременно → одна 201, одна 409, «осиротевшего» клиента нет).
- **Привязка и смена** — compare-and-set по `expectedCustomerId`: два оператора одновременно → один выигрывает, второй получает 409, тихой перезаписи нет (тест).
- Глобальных блокировок нет — не потребовались.

### 17. Tenant isolation/security
- Тенант и бизнес — только из сессии.
- Диалог, клиент, автомобили и обращение ищутся в рамках тенанта + бизнеса.
- Запись привязки ограничена `tenantId + businessId + id + ожидаемым клиентом` (тест `tenantIsolation`).
- Совпадения по телефону — только своего бизнеса.

Тесты подтверждают:
- без сессии → 401;
- чужой клиент → 404;
- чужой диалог — 404 для link / create / vehicle, ничего не изменено;
- поиск дубликата не раскрывает чужого клиента;
- `customerRequestId` в теле игнорируется;
- менеджер: привязка — да, создание клиента и автомобиля — 403 (как на экранах «Клиенты» / «Автомобили»).
