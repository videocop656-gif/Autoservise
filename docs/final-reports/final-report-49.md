## Final Report — Prompt 49: Conversation → Customer Request Operational Bridge

**Итог: PASS.** Оператор создаёт обращение прямо из карточки диалога: данные подставлены, их можно проверить и изменить, затем «Создать обращение». Диалог показывает «Обращение создано» и открывает существующее обращение.

- Работает идемпотентно (повторы, двойные клики, 10 параллельных запросов → одно обращение).
- Транзакционно и с изоляцией тенантов.
- **Без изменения схемы и без миграции** — используется уже существующая связь `Conversation.customerRequestId`.
- Push не выполнялся, Prompt 50 не начинался.

### 2. Architecture audit
| Вопрос | Факт |
|---|---|
| Связь Conversation ↔ CustomerRequest | **Уже есть:** `Conversation.customerRequestId` (nullable FK, индекс, `onDelete: Restrict`); обратная связь `CustomerRequest.conversations`. Проверяется по тенанту в `conversationService.assertRelations` |
| Хранит ли CustomerRequest источник | `source`: PHONE / WEBSITE / MANUAL / OTHER (без «диалога»); связь с диалогом хранится самим FK |
| Conversation ↔ Customer | `Conversation.customerId` (nullable). Входящие Telegram-диалоги получают клиента автоматически (`resolveCustomerForInbound`); ручные могут быть без клиента |
| Conversation ↔ Vehicle | Прямой связи нет; автомобиль — через клиента или обращение |
| tenant / business | Все репозитории через `withTenant(tenantId, { businessId, … })`; AuthContext с сервера |
| Создание CustomerRequest | `createCustomerRequest`: роль owner/admin/manager, проверки владения (клиент активен, авто принадлежит клиенту, услуга активна), статус `NEW` + запись истории |
| Скрытый shortcut в UI | Связать можно только в форме *создания* диалога; в карточке диалога — только показ связанной заявки |
| Статусы обращения | NEW → IN_PROGRESS / WAITING_CUSTOMER → QUALIFIED → CONVERTED; терминальные — CONVERTED / CLOSED / CANCELLED |
| Один диалог — одно или несколько обращений | Одна FK-колонка ⇒ **не более одного** обращения на диалог — ровно правило v1 |

**Важная находка:** английские сообщения валидации обращений — часть внутреннего контракта AI-инструментов (`aiTools` сопоставляет, например, «Customer is not active» с `CUSTOMER_INACTIVE`). Поэтому их нельзя переводить в общих сервисах; мост переводит их на своей границе (§14).

### 4. Relationship decision
Используется существующий `Conversation.customerRequestId`:
- одна колонка на стороне диалога и есть ограничение «не более одного основного обращения на диалог»;
- новая колонка `CustomerRequest.conversationId` дублировала бы связь;
- уникальный индекс не нужен, потому что у диалога физически одно значение FK.

Идемпотентность обеспечивает блокировка строки диалога (§7).

### 6. API implementation
**`POST /api/conversations/:id/request`** — рядом с существующим `POST /api/conversations/:id/messages`, в той же REST-архитектуре и в той же форме, что `POST /api/follow-ups/:id/request` из 48.

- **Тело запроса:**
  - `subject` (обязательно, 2–200);
  - `description` (до 10 000);
  - `vehicleId` / `serviceId` (необязательно);
  - `customerId` — только для диалога без клиента.
- **Решает сервер:** источник, начальный статус, связь; поля status / source / appointment / tenant отбрасываются.
- **Ответы:**
  - 201 — `{ conversation, customerRequest, created: true }` (создано);
  - 200 — `{ …, created: false }` (уже связано);
  - 400 — валидация;
  - 404 — чужое или несуществующее;
  - 409 — редкий конфликт.
- **Источник** — существующий enum по каналу диалога: PHONE → PHONE, WEBSITE → WEBSITE, MANUAL → MANUAL, TELEGRAM / WHATSAPP / OTHER → OTHER. Второй системы источников нет.
- **Сводка связанного обращения** в `GET /api/conversations/:id` расширена полями `vehicleId`, `serviceId`, `createdAt` — это тот же один запрос к БД, без N+1; список диалогов не менялся.

### 7. Idempotency strategy
Двухфазная схема, проверенная в 48.1:
1. **Вне транзакции — все чтения и проверки:** диалог; если уже связан — сразу 200 с тем же обращением; клиент / авто / услуга через правила обращения.
2. **Короткая транзакция только на своём соединении:**
   - `SELECT … FOR UPDATE` строки диалога — по `id` + `tenantId` + `businessId`;
   - повторная проверка;
   - вставка обращения и истории;
   - запись `customerRequestId` (и `customerId`, если его не было).

Параллельные вызовы ждут на блокировке; первый создаёт, остальные видят связь и возвращают то же обращение. Блокировка кнопки в UI — только удобство.

### 8. Concurrency results
| Где | Результат |
|---|---|
| Тесты (модель транзакции с откатом и сериализацией) | 10 параллельных → 1 обращение, все ответы с одним id, без сирот |
| **Supabase, HTTP, 10 параллельных на новый диалог** | **1 × 201 + 9 × 200**, ровно **1** новое обращение, один id во всех ответах, диалог связан, ни одного 500 |
| Supabase, 10 повторов на уже связанный диалог | 10 × 200, `created: false`, тот же id |

Мутационная проверка подтвердила, что тесты ловят регрессии:
- убрана повторная проверка внутри блокировки → падает тест конкурентности;
- записи вынесены из транзакции → падают тесты конкурентности и отката.

### 9. Transactional integrity
- Вставка обращения, запись истории и связывание диалога — одна транзакция.
- Тесты: сбой связывания → обращение и история откатаны, повтор успешен; сбой вставки → диалог не связан и клиент не записан.
- Попутно исправлен неверный тип: `conversationRepository.updateById` был объявлен с реляционным типом Prisma, хотя это `updateMany`, принимающий только скалярные поля; реляционная запись (`connect`) упала бы во время выполнения. Тип заменён на скалярный.

### 10. Tenant isolation
- Сервер проверяет всё: диалог, клиента, авто и услугу — через tenant-scoped репозитории.
- Чужой диалог → 404 «Диалог не найден»; ничего не создаётся и не связывается.
- Чужой клиент / авто / услуга → 404 «Клиент / Автомобиль / Услуга не найден(а)».
- Связанное обращение другого тенанта через мост не читается.
- Тесты: 8 сценариев в `conversationRequestBridge.test.ts` и 2 в `tenantIsolation.test.ts` (блокировка и запись связи ограничены тенантом).
- На Supabase другой тестовый тенант получил 404 на GET и на создание; диалог остался не связан.

### 12. Customer / Vehicle / Service behavior
- **Клиент:** клиент диалога всегда переиспользуется и показывается без выбора; попытка передать другого → 400. Диалог без клиента предлагает выбрать существующего и даёт ссылку «Создайте его в разделе «Клиенты»». Выбранный клиент записывается и в диалог (в той же транзакции). Дубликатов не создаётся.
- **Автомобиль:** если у клиента ровно один автомобиль, он выбран; если несколько — выбор; «Не указан» допустим (как и сейчас в обращениях). Принадлежность проверяется на сервере.
- **Услуга:** выбор из активных; «Не указана» допустима; никаких догадок и AI.
- **Предзаполнение** (детерминированное, без AI): тема — тема диалога или «Обращение из диалога (канал)»; описание — последнее входящее сообщение клиента с подписью «Подставлено последнее сообщение клиента — можно изменить.».

### 23. Remaining limitations
1. **Одно обращение на диалог** (v1). Несколько работ из одного диалога — отдельное продуктовое решение.
2. **Существующий PATCH диалога** по-прежнему позволяет вручную перепривязать `customerRequestId` (функция из более ранних промптов); мост его не использует.
3. **Нового клиента из формы не создать:** ссылка ведёт в раздел «Клиенты».
4. **Поля форм, которые выбирают клиента, автомобиль и услугу**, пользуются справочниками страницы (до 100 записей); сервер при этом проверяет любой id.
5. **Страницы `/requests` и `/conversations` убирают `?open=` из адреса** после открытия (так было и раньше): обновление страницы возвращает к списку.
6. **Остальные английские сообщения валидации** более ранних промптов вне моста не переводились (§24).
7. **Тестовые данные** «Проверка P48.1 / P49» остаются в тестовых тенантах.
