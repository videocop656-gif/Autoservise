## Final Report — Prompt 55: AI-Assisted Request Qualification

**Итог: PASS.** В карточке диалога появился раздел **«Разбор обращения»**. По кнопке «Разобрать обращение» AI читает настоящий диалог и предлагает структурированное обращение:
- услугу из настроенных;
- сохранённый автомобиль клиента;
- описание потребности;
- желаемые дату и время.

Отдельно — чего не хватает для записи. **Пока оператор не подтвердит, ничего не сохраняется.** После проверки и правки оператор нажимает «Создать обращение» (через существующий мост Prompt 49) или «Обновить обращение» (через существующий `updateCustomerRequest`).

Модель **никогда не передаёт id**: только названия и даты, как их написал клиент. Сервер сам сопоставляет их с данными тенанта. Схема Prisma не менялась, миграций нет.

### 1. Audit findings
- **`CustomerRequest`:**
  - обязательные — `customerId`, `subject` (2–200);
  - необязательные — `vehicleId`, `serviceId`, `appointmentId`, `description` (до 10 000), `notes`;
  - `source` (MANUAL / PHONE / WEBSITE / OTHER); `status` (по умолчанию NEW).
  - **Для времени уже есть канонические поля:** `requestedDate` (желаемый **день**, хранится как UTC-полночь местной даты бизнеса), `requestedTimeFrom` / `requestedTimeTo` («HH:mm»).
- **Статусы:** NEW → IN_PROGRESS → WAITING_CUSTOMER / QUALIFIED → CONVERTED; CLOSED / CANCELLED; CONVERTED / CLOSED / CANCELLED — терминальные. Создание всегда даёт NEW.
- **Правила** (`prepareCustomerRequestCreate` / `updateCustomerRequest`):
  - клиент, автомобиль, услуга и запись — своего тенанта;
  - автомобиль принадлежит клиенту;
  - услуга активна;
  - время «с» раньше «до»;
  - при обновлении связи перепроверяются только изменённые поля.
- **Мост P49** (`createCustomerRequestFromConversation`): атомарно создаёт и привязывает обращение через `linkCustomerRequest` (P49.1), клиент — из диалога, идемпотентен (повтор возвращает существующее с `created:false`). Полей времени в нём не было.
- **AI:**
  - единое ядро `runAnalysis` с режимами (P53);
  - строгий структурированный вывод **уже существует** — `AiResult` (OpenAI `response_format: json_schema` strict + Zod `aiResultSchema`);
  - в нём `entities`: `customerName`, `phone`, `vehicleMake`, `vehicleModel`, `licensePlate`, `serviceName`, `requestedDate`, `requestedTime`;
  - контекст содержит текущую дату бизнеса, часы, услуги, связанного клиента и его сохранённые автомобили (P53 / P54).
- **Чего нет:** id в выводе модели и полей «уверенности» по отдельным сущностям — есть только общий `confidence` / `needsHuman`.

### 2. CustomerRequest domain mapping
| Предложение | Поле `CustomerRequest` | Источник |
|---|---|---|
| Клиент | `customerId` | **только** `Conversation.customerId` (P54), никогда не AI |
| Автомобиль | `vehicleId` | один из сохранённых автомобилей клиента; выбирает оператор |
| Услуга | `serviceId` | активная настроенная услуга; выбирает оператор |
| Тема | `subject` | у связанного обращения — его тема, иначе название услуги или начало описания; правится |
| Потребность | `description` | фактическое описание от AI; правится |
| Дата | `requestedDate` | местная дата бизнеса `YYYY-MM-DD` |
| Время | `requestedTimeFrom` / `requestedTimeTo` | «после 15» → с 15:00; «до» — вручную |

Новых полей нет — анализ AI не хранится, хранится только то, что подтвердил оператор.

### 3. Structured qualification contract
**Вывод модели** — существующий `AiResult` (второго контракта нет). В режиме `qualify` промпт задаёт смысл полей:
- `answer` — 1–3 предложения фактов для сотрудника;
- `entities.serviceName` — **точное** название одной услуги из списка или `null`;
- `vehicleMake` / `vehicleModel` / `licensePlate` — как написал клиент;
- `requestedDate` — `YYYY-MM-DD` по `currentDateTime`;
- `requestedTime` — с какого времени;
- `customerName` / `phone` — только если клиент написал их сам.

Вывод проходит Zod (`aiResultSchema`) и слой безопасности.

**Ответ сервера** — `POST /api/conversations/:id/qualification {action:"analyze"}` → `qualification`:
- `basedOn` `{customerId, customerRequestId, requestUpdatedAt}` — снимок для проверки устаревания;
- `customer` — `linked {id, name, phone}` | `missing {mentionedName, mentionedPhone}`;
- `vehicle` `{status, vehicleId, mention}`, где `status` ∈ `request` | `matched` | `single` | `ambiguous` | `unverified` | `none` | `no_customer`, и `vehicleOptions`;
- `service` `{status, serviceId, mention}`, где `status` ∈ `request` | `matched` | `unresolved`, и `serviceOptions`;
- `subject`, `description`;
- `timing` `{requestedDate, requestedTimeFrom, requestedTimeTo, notes[]}`;
- `missing[]`, `needsHuman`.

### 4. Trusted vs unverified data handling
**Проверенные** (из базы, своего тенанта): связанный клиент, его сохранённые автомобили, настроенные услуги, связанное обращение, часы, дата.

**Непроверенные** (слова клиента), в интерфейсе всегда помечены:
- «Из сообщения (не проверено): Пётр, +7…»;
- «Из сообщения: «Camry 2021» — такого автомобиля у клиента нет…»;
- «AI: «…» — нет среди услуг».

Непроверенное **никогда** не становится id: автомобиль или услугу можно сохранить только выбором из сохранённых / настроенных.

### 5. Customer behavior
- **Клиент привязан** — он единственный источник; имя, найденное моделью, его не заменяет (тест).
- **Клиента нет** — «Клиент не определён — свяжите или создайте его в разделе «Клиент и автомобиль»» (P54), плюс имя и телефон из сообщения как непроверенные. «Создать обращение» недоступно; на сервере → 409 «Сначала свяжите диалог с клиентом.»
- Создания и привязки клиента нет.

### 6. Vehicle matching behavior
Порядок (сервер):
1. Нет клиента → `no_customer`.
2. Есть связанное обращение с автомобилем → `request`.
3. Клиент назвал автомобиль → сначала точный госномер (без пробелов, верхний регистр). Иначе сохранённая **модель** должна входить в названное клиентом, а если клиент назвал марку — и марка. Одно совпадение → `matched` (предложено, «проверьте»); несколько → `ambiguous` («Нужно выбрать автомобиль»); ни одного → `unverified` с указанием на «Добавить автомобиль».
4. Автомобиль не назван: один сохранённый → `single` («единственный автомобиль клиента — проверьте»); несколько → `ambiguous`; ни одного → `none`.

Выбор — только из автомобилей клиента этого бизнеса. Автомобиль не создаётся и не переносится.

### 7. Service matching behavior
- С привязанным обращением, у которого есть услуга → `request`.
- Иначе `entities.serviceName` должно **точно** (без учёта регистра) совпасть с названием **активной** услуги **этого** бизнеса → `matched`.
- Во всех остальных случаях → `unresolved` «Услуга требует уточнения.»: неактивная услуга, неизвестное название, название чужого тенанта, id вместо названия, несколько подходящих, расплывчатый симптом (тесты).
- Оператор может выбрать любую активную услугу в списке; сохраняются только id настроенных услуг.

### 8. Description/need summarization
- `description` — фактическое описание от AI.
- Промпт запрещает диагноз и предположения о причине. Слой безопасности (`applyDefinitiveDiagnosisCheck`) отклоняет утверждённый диагноз — тогда описание пустое и в «не хватает» пишется «Описание не сформировано автоматически — заполните его вручную.» (тест).
- Mock-провайдер даёт пересказ «Клиент пишет: «…»» (браузер: «Что-то стучит спереди» → без диагноза).
- Описание правится оператором.

### 9. Timing preference handling
- Канонические поля есть, поэтому время сохраняется в них, а не в описании.
- Дата вычисляется моделью по `currentDateTime` бизнеса (P53).
- Сервер оставляет только реальную (не «30 февраля») и не прошедшую местную дату и время формата HH:mm. Остальное отбрасывается с пометкой («Дата из сообщения не распознана.», «…уже прошла.», «Время … не распознано.»).
- «После 15» → «с 15:00»; «до» — вручную. Оператор правит дату и время.
- При сохранении дата передаётся как местный полдень бизнеса → `requestedDate` = этот день. Запись (Appointment) не создаётся.

### 10. Missing-information logic
Детерминированно, по фактическим требованиям следующего шага. Запись на обслуживание требует клиента, автомобиль, услугу и время. Для самого обращения обязательны только клиент и тема.

Пункты «Для записи не хватает»:
- клиент не связан;
- автомобиль не выбран / нужно выбрать / автомобиль из сообщения не сохранён;
- «Услуга требует уточнения.»;
- «Клиент не указал удобную дату.»;
- (при отклонённом описании) заполнить описание.

Госномер, VIN и пробег **не** требуются — их нет в требованиях записи.

### 11. Conversation qualification UX
Раздел «Разбор обращения» стоит между «Клиент и автомобиль» и «Обращение». Кнопка «Разобрать обращение» (иконка списка, без «AI-эффектов»).

Состояния:
- «AI анализирует обращение…» (кнопка неактивна);
- форма проверки;
- ошибка «Не удалось разобрать обращение. Попробуйте ещё раз.» (без автоповтора);
- без сообщений клиента кнопка неактивна с пояснением.

После сохранения — «Обращение создано и связано с диалогом.» / «Обращение обновлено.» Сообщение хранится в карточке диалога: перезагрузка после сохранения пересоздаёт раздел — ошибка найдена при проверке в браузере и исправлена.

### 12. Operator edit/review behavior
- **Поля:** автомобиль (выбор), услуга (выбор), тема, «Что нужно клиенту», дата / с / до — всё правится. Клиент только отображается.
- **Подсказки** — пометки статуса (предложено / проверьте / нужно выбрать / из сообщения), заметки по времени и список «не хватает».
- «Закрыть» отбрасывает предложение без записи.

### 13. New Request creation behavior
`{action:"create"}` идёт **через мост P49**:
- клиент диалога; существующие правила (автомобиль клиента, активная услуга, клиент активен);
- источник из канала; статус **NEW** + запись истории;
- атомарное создание + привязка через `linkCustomerRequest`;
- запись (Appointment) не создаётся.

В мост добавлены только необязательные поля времени, обратно совместимо: все 32 теста моста без изменений. Если мост вернул уже существующее обращение (`created:false` — кто-то успел раньше) → 409.

### 14. Existing Request update behavior
`{action:"update"}` → существующий `updateCustomerRequest`:
- передаются **только изменившиеся** поля (автомобиль, услуга, тема, описание, дата, время);
- **никогда** — клиент, статус, запись;
- второе обращение не создаётся;
- связь диалога с обращением не меняется.

Завершённое обращение (CONVERTED / CLOSED / CANCELLED) не меняется: 409 «Обращение уже завершено — изменять его нельзя.»

### 15. Request status behavior
Статус не меняется ни анализом, ни подтверждением. Создание — NEW (правило создания), обновление статус не трогает. Анализ AI ≠ квалификация бизнеса: перевод в QUALIFIED по-прежнему делает оператор в карточке обращения (переходы NEW → IN_PROGRESS → QUALIFIED).

### 16. AI core reuse
Один `runAnalysis` с новым режимом `qualify`:
- тот же провайдер, системный промпт (плюс блок режима) и контекст (дата, часы, услуги, Knowledge, Rules, клиент, автомобили);
- та же история (последние 20 до последнего сообщения клиента);
- тот же Zod / слой безопасности / аудит `AiLog` (`metadata.mode = qualify`).

Провайдер получает необязательное `mode` — чисто информационное поле; реальной модели достаточно промпта.

### 17. AI execution safety / blocked tools
- **Ни одного инструмента:** в режиме `qualify` провайдеру не предлагается ничего, даже проверка доступности. Любой запрос инструмента отклоняется **до реестра** (`isToolAllowed('qualify', …) = false`).
- **Эскалация** не создаётся.
- **Не создаются:** Message, доставка, вызов Telegram, обращение, клиент, автомобиль, запись.
- Сохраняет только отдельное действие оператора.
- **Мутационная проверка:** если открыть шлюз, падают 3 теста.

### 18. Structured-output validation
- Неверная форма / JSON → 502 `AI_QUALIFICATION_UNAVAILABLE` «Не удалось разобрать обращение…»; полу-доверенного предложения нет.
- Сбой провайдера → тот же текст с исходным кодом.
- Значения внутри валидной формы проходят серверную очистку (§6–§9).

### 19. Hallucinated-ID protection
- Модель **не может** передать id: контракт содержит только названия. Даже UUID в `serviceName` (свой или чужой) не сопоставляется (тест).
- При сохранении id приходят из формы оператора и проверяются заново существующими правилами:
  - чужой или выдуманный `serviceId` → 404 «Услуга не найдена»;
  - чужой `vehicleId` → 404 «Автомобиль не найден»;
  - автомобиль другого клиента → 400 «Автомобиль не принадлежит выбранному клиенту»;
  - неактивная услуга → 400.
- `customerId` / `customerRequestId` из тела игнорируются: клиент — из диалога, а связь обращения пишет только мост.

### 20. Stale/concurrent-state behavior
Предложение — снимок. При сохранении сервер заново проверяет:
- клиент диалога = `expectedCustomerId`;
- для создания — обращения ещё нет (и мост не вернул чужое существующее);
- для обновления — то же обращение и тот же `updatedAt`.

Любое расхождение → 409 `QUALIFICATION_STALE` «Данные обращения изменились. Обновите разбор и проверьте его ещё раз.» Услуга, ставшая неактивной, и чужие или «уехавшие» автомобили отсекаются правилами сервиса.

Ограничение: между проверкой `updatedAt` и записью есть узкое окно (обновление идёт через существующий сервис без условной записи).

### 21. Tenant isolation/security
Тенант — из сессии. Диалог, клиент, обращение, автомобили и услуги ищутся в его рамках; списки вариантов — только этого бизнеса.

Тесты: чужой диалог → 404; без сессии → 401; чужая услуга не сопоставляется; чужие id при сохранении → 404. Роли — owner / admin / manager, как у остальных действий с обращениями.
