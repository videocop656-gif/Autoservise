## Final Report — Prompt 48.3: Database Connection Performance Audit & Safe Configuration

**Итог: PASS.**

- **Корень проблемы** — не пулер Supabase и не код приложения, а сочетание трёх факторов:
  - Prisma в режиме `pgbouncer=true` делает ≈5 сетевых обменов на запрос;
  - через transaction pooler этот режим обязателен;
  - база далеко: ~225 мс на обмен от машины разработчика до Tokyo.
- **Исправление** — только конфигурация и документация:
  - локальный `DATABASE_URL` переведён на session pooler `:5432`;
  - для Vercel задокументирован transaction pooler `:6543` c `pgbouncer=true&connection_limit=1`;
  - миграции без изменений идут через `DIRECT_URL` `:5432`.
- **Результат:** один запрос к БД локально ~1150 → ~225 мс, `/operations` (API) 17.4 → 4.4 с, без ошибок.
- Код приложения, схема и миграции не менялись. Push не выполнялся, Prompt 49 не начинался.

### 3. Root-cause analysis
Замеры по слоям — медианы по 7 запросам:

| Слой | `:6543` transaction | `:5432` session |
|---|---|---|
| TCP connect (≈ 1 сетевой обмен) | 236 мс | 225 мс |
| raw `pg`: `SELECT 1` | **230 мс** | 221 мс |
| Prisma: `SELECT 1` | **1150 мс** | 225 мс |
| Prisma: `service.findFirst` | 1177 мс | 228 мс |
| Prisma на `:6543` **без** `pgbouncer=true` | не завершилось за 240 с | — |

Выводы:
- **Сам transaction pooler не медленный:** обычный драйвер тратит один обмен (~230 мс), как и session pooler.
- **~1.1 с даёт Prisma в режиме `pgbouncer=true`:** ≈5 обменов на запрос (1150 ≈ 5 × 225).
- **Без флага** Prisma на `:6543` зависает (конфликт кэшированных prepared statements), поэтому флаг для `:6543` обязателен — «ускорить» простым удалением нельзя.
- **Итог:** локальный Node-процесс шёл через режим, предназначенный для serverless. Помноженный на удалённость БД, он давал ~1.1 с на **каждый** запрос, и `/operations` (≈11 параллельных вызовов на пуле 5) подходил к 10-секундному таймауту пула.

### 7. Vercel / serverless recommendation (не развёрнуто, настройки Vercel не менялись)
- **`DATABASE_URL` на Vercel** = transaction pooler `:6543` c `?pgbouncer=true&connection_limit=1`:
  - каждый экземпляр функции держит одно соединение, Supavisor мультиплексирует их;
  - это защищает от исчерпания соединений при многих одновременных функциях и холодных стартах;
  - `pgbouncer=true` обязателен (§3).
- **`DIRECT_URL`** = session pooler `:5432` — только для миграций (локально или в CI), не в рантайме.
- **Регион функций — рядом с БД** (Vercel `hnd1`, Tokyo), если позволяет план. Тогда ~5 обменов Prisma стоят миллисекунды, а не секунды. Из далёкого региона transaction pooler повторит нынешнюю медлительность.
- `.env` не попадает в Vercel. Переменные задаются в проекте Vercel; `NODE_ENV=production` Vercel ставит сам.

### 9. PrismaClient lifecycle audit
- `src/server/db/prisma.ts`: один `PrismaClient`, кэшируемый в `globalThis` вне production, — при горячей перезагрузке Vite (`ssrLoadModule`) новые клиенты не создаются. **Дефекта нет, код оставлен как есть.**
- Других `new PrismaClient` в рантайме нет; `prisma/seed.ts` — отдельный разовый скрипт.
- При смене `.env` Vite сам перезапускает сервер («.env changed, restarting server») — это новый процесс, а не утечка клиентов.
- На Vercel каждый экземпляр функции создаёт свой клиент, поэтому там `connection_limit=1`.

### 11. Region-latency assessment
- **География:** TCP connect ≈ 225 мс, raw `SELECT 1` ≈ 221–230 мс — это чистая сетевая задержка от машины разработчика до `ap-northeast-1`, нижняя граница для любого запроса отсюда.
- **Накладные расходы пула / Prisma:** на `:6543` +≈925 мс на запрос (≈4 лишних обмена) — **устранены** локально переходом на `:5432`.
- **Остаток** — сетевая задержка × число последовательных запросов. Каждый API-запрос сначала проходит авторизацию: ≈4 последовательных запроса ≈ 0.9 с (`auth/me` после исправления ≈ 995 мс). Дальше — собственные запросы эндпоинта.
- Лечится размещением рантайма рядом с БД (§7), а не конфигурацией. Регион БД не менялся.

3. **Кратковременный сбой связи.** Во время Prompt 48.2 в логе был одномоментный `Can't reach database server` (5 ошибок в одну миллисекунду, затем норма) — временный сбой сети или Supabase, а не конфигурация.
